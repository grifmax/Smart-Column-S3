# Обкатка на воде (Mode::WATER_TEST)

Режим проверяет железо, гидравлику и защиты **без спирта**. Вода кипит при
99-100 °C, что выше порогов `BODY→TAILS` (94.5 °C) и `TAILS→FINISH` (99.0 °C),
поэтому на воде целиком проходится настоящий конечный автомат ректификации.

Режим ничего не разрешает и не ослабляет: все штатные интерлоки остаются
включёнными, потому что смысл прогона — проверить именно их.

## Подготовка

1. Заполнить куб водой выше ТЭНа и выставить фактический объём в
   `rectParams.feedVolumeL` — шаг предполётной проверки сверяет его с
   `minHeaterSubmergeL`.
2. Открыть кран охлаждающей воды. Клапан воды должен быть помечен как НО
   (`valveNormallyOpenMask`, бит 0).
3. Убедиться, что датчик давления либо установлен, либо отсутствует осознанно:
   шаги давления будут пропущены (SKIP), остальные выполнятся.
4. Подготовить весы и мерную ёмкость для шага отбора.

## Запуск

```
curl -X POST http://<IP>/api/water-test/start
curl http://<IP>/api/water-test/status
```

Остановка в любой момент:

```
curl -X POST http://<IP>/api/water-test/stop
```

## Шаги

| Шаг | Что делает | Длительность |
|---|---|---|
| `precheck` | обязательные датчики, разброс температур, присутствие и нуль датчика давления, объём над ТЭНом, проток воды | 5 с |
| `heat_full` | 100 % мощности: сверка PZEM с уставкой, рост температуры, импульсы zero-cross | 10 мин |
| `heat_low` | 30 %: линейность фазового управления | 10 мин |
| `cooling` | проток и ΔT воды, расчёт теплосъёма дефлегматора | 2 мин |
| `pressure_curve` | три ступени мощности (40/70/100 %), dP каждой, оценка коэффициента насадки | 15 мин |
| `takeoff` | 300 мл/ч × 10 мин, затем ожидание замера | 10 мин + ожидание |
| `fsm_run` | полный прогон ректификации: HEATING→STAB→HEADS→POST_HEADS→PURGE→BODY→TAILS→FINISH на тест-профиле 50/300/50 мл | до 4 ч |
| `injection_water_off` | клапан воды закрыт на 120 с: ожидается `LOW_WATER` | 2 мин |
| `injection_pressure_block` | обнуление давления при кипении: ожидается предупреждение «датчик не видит нагрузку» | 1 мин |
| `injection_sensor_drop` | отвал датчика ТСА: ожидается `SENSOR_FAILURE` и остановка режима | 30 с |

Инъекция отвала датчика идёт последней: она защёлкивает настоящую аварию и
останавливает режим, поэтому всё, что должно выполниться, выполняется до неё.

## Замер объёма на шаге отбора

```
curl -X POST "http://<IP>/api/water-test/measure?valueMl=48.7"
```

Без замера шаг завершится через 30 минут со статусом SKIP.

## Отчёт

```
curl http://<IP>/api/water-test/report
```

Отдаёт массив проверок с полями `step`, `id`, `verdict` (`pass`/`warn`/`fail`/
`skip`), `expected`, `actual`, `note`, плюс замеры и шаг прерывания. Те же
строки пишутся в системный лог с префиксом `watertest`.

## Как читать результат

- `fail` по `power_match` — ТЭН, симистор или неверная паспортная мощность.
- `fail` по `zero_cross` — детектор нуля мёртв: уставка есть, нагрева нет.
- `fail` по `cooling_capacity` — дефлегматор не держит мощность ТЭНа; на спирте
  это прорыв по ТСА.
- `fail` по `pump_volume` — срыв прайма или неверная калибровка `мл/об`.
- `warn` по `packing_coeff` — это оценка, а не измерение: значение требует
  проверки на спирте.

## Известные ограничения

Проверки, которые сейчас заведомо дают `fail`, потому что соответствующий
интерлок ещё не реализован в прошивке:

- `trip_low_water` — нет интерлока по протоку охлаждающей воды;
- `pressure_no_load` — нет перекрёстной проверки «датчик давления не видит
  нагрузку при кипении».

Эти строки в отчёте — не дефект обкатки, а список того, что нужно закрыть в
прошивке.
