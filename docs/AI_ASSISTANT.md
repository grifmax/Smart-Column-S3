# AI-ассистент в Web UI

Документ описывает встроенный чат с ИИ: откуда он берёт данные, что именно
отправляет модели, какие действия ему разрешены и как его предложения
попадают в историю прогонов. Код: `src/web/ai/`.

## Границы

- ИИ работает **только на чтение**. У него нет инструментов управления
  нагревом, насосом, клапанами, старта/стопа процесса. Это сознательное
  ограничение первого этапа: прибор управляется человеком через Web UI и TFT,
  а модель объясняет данные и предлагает изменения параметров.
- Модель — облачная, OpenAI-совместимая. Ключ и адрес провайдера хранятся в
  `localStorage` браузера и **не попадают в прошивку и NVS**.
- Модель ничего не «помнит» между сессиями на приборе. Память — это пакеты
  контекста, которые фронтенд собирает из API, плюс журнал предложений,
  сохранённый в браузере.

## Почему не сырые данные

| Источник | Что есть | Ограничение |
|---|---|---|
| `/api/status` | полное состояние, indicators, guidance | ~9 КБ, меняется ежесекундно |
| `/api/charts/live` | 60 точек по минуте + 72 точки по 10 минут | детальность вне часа теряется |
| `/api/history/{id}` | ряды с шагом 60 с, фазы, метрики | 60 с слишком грубо для анализа управления |
| `/api/logs/events` | до 200 событий на запрос | полного лога в промпт не бывает |

Поэтому прибор считает **агрегаты управления на 1 Гц** (блок `controlStats` в
истории, см. `HISTORY_SCHEMA.md`), а фронтенд собирает из них три компактных
пакета.

## Пакеты контекста

### `state_pack` — текущее состояние (~0.5 КБ)

Собирается из `/api/status`. Содержит режим, фазу, паузу, аварию, температуры,
мощность (задание/факт/ошибка), насос, давление, верхние `guidance` /
`reasonInsight`, 5–7 ключевых indicators и активные лимиты. Уходит в модель в
каждом запросе как «текущая обстановка».

### `phase_pack` — фаза (из истории)

Поля фазы (`name`, `duration`, `startTemp`, `endTemp`, `volume`, `avgSpeed`,
`reasonCode`) плюс вложенный `control`: средняя/максимальная мощность,
средний и максимальный duty нагрева, время в насыщении, время «просили
мощность — не получили», время в температурной полосе, перерегулирование,
средний health/stability, максимум floodRisk, минимум coolingMargin, средняя и
пиковая скорость роста давления, паузы, секунды degraded, число safety-trip.

### `run_pack` — прогон (~2–4 КБ)

Метаданные, параметры запуска, таблица фаз с `control`, метрики прогона
(`metrics`), `controlStats` за весь прогон, элементы `advisorSnapshot`,
ошибки/предупреждения и **прореженный** ряд (не более 40 точек по 60-секундной
сетке), чтобы модель видела форму кривой, но не получала килобайты.

### `log_digest` — журнал

Счётчики по уровням и последние 30 событий с временем, уровнем, сообщением и
`reasonCode`. Полный CSV доступен человеку отдельно, модели он не нужен.

## Инструменты (read-only)

| Инструмент | API | Что делает |
|---|---|---|
| `get_status` | `GET /api/status` | компактный `state_pack` |
| `get_health` | `GET /api/health` | heap, uptime, sensors, control-метрики |
| `list_processes` | `GET /api/history` | список прогонов с итогами |
| `get_process` | `GET /api/history/{id}` | `run_pack` одного прогона |
| `get_logs` | `GET /api/logs/events` | `log_digest` за окно времени |
| `get_live_chart` | `GET /api/charts/live` | минутный и 10-минутный ряды |
| `compare_runs` | два `get_process` | дельта метрик и `control` |

Каждый результат обрезается до ~6 КБ. Если модели нужно больше, она делает
несколько точечных вызовов, а не один гигантский.

## Предложения по улучшению

Ответ модели — обычный текст плюс необязательный JSON-блок:

```json
{
  "findings": [
    {"code": "power_saturation", "detail": "Нагрев 100 % в течение 12 мин на фазе body", "evidence": "phases[3].control.saturationSec=720"}
  ],
  "proposals": [
    {
      "parameterKey": "phasePowerPercent.body",
      "previousValue": 60,
      "suggestedValue": 65,
      "expectedEffect": "Сократить время фазы на 8–12 %, без роста floodRisk выше 0.4",
      "confidence": 0.6,
      "evidence": "control.powerAvgW 1180 при задании 60 %, saturationSec 0"
    }
  ]
}
```

Фронтенд рисует `findings` как наблюдения, `proposals` — как карточки.
«Принять» сохраняет предложение в локальный журнал `sc3.ai.proposals` и
показывает его в истории чата; применение к профилю остаётся ручным действием
оператора. Следующий прогон даёт измеренный эффект, и журнал «предложение →
исход» попадает в системный промпт как накопленный опыт.

## Настройки провайдера

Настройки живут **в NVS прибора** (`/api/ai/config`, GET/POST) — один раз
введённые адрес, ключ и модель подхватываются на телефоне, планшете и ноутбуке.
Копия в `localStorage` остаётся кэшем для первой отрисовки и работает, если
прибор недоступен.

Важно: ключ хранится в приборе в открытом виде и отдаётся по GET любому
клиенту, у которого есть доступ к веб-интерфейсу. Если это неприемлемо —
включайте Basic Auth в настройках безопасности или не сохраняйте ключ на
прибор.

`sc3.ai.provider` в `localStorage` (кэш):

```json
{
  "baseUrl": "https://api.deepseek.com/v1",
  "apiKey": "",
  "model": "deepseek-chat",
  "temperature": 0.2,
  "maxTokens": 2000
}
```

Список моделей запрашивается у провайдера (`GET {baseUrl}/models`). Если
провайдер закрывает endpoint, id вводится вручную. Для локальной модели
(Ollama/LM Studio) ключ не нужен, но браузер должен иметь сетевой доступ к
хосту модели.

## Приватность

- Наружу уходят только пакеты, перечисленные выше, и вопрос оператора.
- Сырые ряды, полный CSV и настройки прибора в облако не отправляются.
- Ключ хранится в браузере; очистка данных сайта его удаляет.

## Ограничения и следующий шаг

- Управление (старт/стоп/уставки) сознательно не подключено. Если появится,
  только через существующие `/api/process/*` и `safety.cpp`, с подтверждением
  каждой команды и отдельным режимом «Оператор».
- Стриминг ответа пока не обязателен: запрос нестриминговый, с кнопкой отмены.
- Долгое накопление данных (датасет для дообучения) требует внешнего
  коллектора: прибор хранит 50 прогонов и 10 файлов лога.
