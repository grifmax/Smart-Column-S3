# План переработки раздела "Оборудование -> Тестирование"

## Цель

Подготовить новый подпункт `Тестирование` внутри меню `Оборудование`, в котором каждый физический узел системы будет вынесен в отдельную полезную сервисную группу. Раздел должен помогать:

- быстро проверять исполнительные устройства по одному;
- видеть живые показания датчиков рядом с тестовыми действиями;
- безопасно запускать потенциально опасные узлы;
- не смешивать сервисные тесты с рабочими режимами и калибровками;
- давать понятный интерфейс для диагностики, а не просто набор кнопок.

Код в рамках этого этапа не внедряется. Документ фиксирует целевую структуру, UX, backend-потребности и порядок реализации.

## Принципиальная идея

Текущий раздел `Оборудование` перегружен и смешивает:

- базовые параметры оборудования;
- калибровку насоса;
- калибровку термометров.

Новая структура должна разделить эти задачи на три подгруппы внутри `Оборудование`:

1. `Параметры`
2. `Калибровка`
3. `Тестирование`

Главный акцент этого плана — именно `Тестирование`.

## Аудит текущего состояния

Сейчас уже есть готовая база, которую нужно не перепридумывать, а аккуратно переиспользовать:

- в `Оборудование` уже существуют:
  - параметры насоса;
  - параметры ТЭНа;
  - параметры куба и колонны;
  - калибровка насоса;
  - калибровка термометров;
- уже есть API и UI для:
  - запуска и остановки насоса;
  - статуса и диагностики насоса;
  - калибровки насоса;
  - сканирования и калибровки термометров;
  - получения текущих значений давления;
  - получения текущих значений ареометра;
- demo-режим уже не должен управлять реальным железом.

Это значит, что новая архитектура тестирования может быть собрана поверх уже существующих узлов, а не с нуля.

## Целевая информационная архитектура

### 1. Внутренняя навигация раздела `Оборудование`

Внутри вкладки `Оборудование` сделать локальную поднавигацию:

- `Параметры`
- `Калибровка`
- `Тестирование`

Ожидаемое поведение:

- `Параметры` — только постоянные настройки железа;
- `Калибровка` — только процедуры калибровки;
- `Тестирование` — только ручная диагностика, живая телеметрия и сервисные включения.

### 2. Общая композиция подпункта `Тестирование`

Внутри `Тестирование` нужен не хаотичный набор карточек, а сервисный layout:

1. Верхняя сервисная панель статуса
2. Блок safety-ограничений и предупреждений
3. Группы оборудования

### 3. Верхняя сервисная панель статуса

В верхней части `Тестирование` должен быть общий sticky-блок:

- `Активен ли процесс`
- `Demo mode`
- `Разрешено ли тестирование`
- `Есть ли активная авария`
- `Какие узлы сейчас уже включены`
- кнопка `Остановить все тесты`

Этот блок нужен, чтобы оператор всегда видел, можно ли вообще безопасно жать тестовые кнопки.

## Общие правила для раздела `Тестирование`

### 1. Тесты не должны конфликтовать с процессом

По умолчанию тестирование должно быть запрещено, если:

- активен рабочий режим;
- сработала авария;
- система находится в состоянии, где ручное управление опасно.

Исключение возможно только для чисто информационных тестов датчиков, которые ничего не включают физически.

### 2. Не смешивать несколько силовых тестов одновременно

Нужна единая политика interlock:

- одновременно разрешать только совместимые тесты;
- для силовых узлов по умолчанию разрешать один активный тест за раз;
- перед запуском нового теста предлагать остановить предыдущий.

Минимально блокировать конфликты между:

- насосом;
- ТЭНом;
- клапанами/сервоприводом;
- калибровочными процедурами.

### 3. Demo mode

В demo-режиме раздел остаётся доступным, но:

- все физические команды подавляются;
- интерфейс явно помечает, что тест "симулируется";
- опасные силовые тесты показывают статус `SIMULATED`, а не `ON`.

### 4. Единый паттерн test-card

У каждой группы должен быть одинаковый каркас:

- заголовок и короткое описание;
- текущий живой статус;
- параметры теста;
- главная action-кнопка;
- вторичные сервисные действия;
- журнал результата;
- safety-подсказки.

Это делает раздел предсказуемым и не превращает его в набор разных mini-приложений.

## Состав групп в `Тестирование`

### 1. Группа `Насос`

#### Назначение

Быстрая проверка вращения, скорости и общего состояния насоса.

#### Что переносим и переиспользуем

- существующую ручную установку параметров насоса;
- существующую калибровку насоса;
- существующие pump status и pump diag.

#### Что должно быть внутри

- текущий статус:
  - `работает / остановлен`;
  - `целевая скорость`;
  - `фактическая скорость`;
  - `объём`;
  - `диагностика worker/task`, если нужна в expanded-виде;
- поле задания скорости вращения/подачи;
- одна главная кнопка:
  - `Запустить насос`
  - после запуска меняется на `Остановить насос`;
- компактный блок "живой отклик":
  - растёт ли объём;
  - меняется ли applied speed;
  - есть ли ошибки/таймауты.

#### Что остаётся отдельно, но рядом

- `Калибровка насоса` лучше хранить в подпункте `Калибровка`, но в карточке `Насос` в `Тестировании` нужна ссылка или action:
  - `Перейти к калибровке насоса`.

#### UX-акценты

- старт/стоп одной кнопкой;
- значения скорости не дёргать слишком часто;
- дать несколько быстрых пресетов:
  - `300`
  - `800`
  - `1500`
  - `3000`
  - `5000`

#### Backend-потребности

Уже есть:

- `POST /api/pump/start`
- `POST /api/pump/stop`
- `GET /api/pump/status`
- `GET /api/pump/diag`

На первом этапе новых API не требуется.

### 2. Группа `Клапаны`

#### Назначение

Ручная проверка всех клапанов по отдельности и быстрый visual-check их отклика.

#### Что должно быть внутри

Для каждого клапана — своя подкарточка или строка:

- имя клапана;
- текущее состояние;
- `Включить`;
- `Выключить`;
- необязательный `Импульс/тест на N секунд`, если это полезно.

#### Отдельно для клапана УНО

Если для УНО есть калибровка, она должна быть выделена как специальная секция:

- текущие параметры;
- запуск калибровки;
- ручное позиционирование;
- сохранение результата.

#### UX-акценты

- цветовое различие `Открыт / Закрыт`;
- не перегружать: одна строка = один клапан;
- для опасных клапанов дать текст-предупреждение, если они меняют поток жидкости/пара.

#### Backend-потребности

Нужно проверить и, скорее всего, добавить/нормализовать test-endpoints:

- `GET /api/valves/status`
- `POST /api/valves/{id}/open`
- `POST /api/valves/{id}/close`
- опционально `POST /api/valves/{id}/pulse`

Если текущих API нет, это отдельная реализационная фаза.

### 3. Группа `Сервопривод`

#### Назначение

Проверка приводов, у которых важно движение по позициям, а не только бинарное состояние.

#### Что должно быть внутри

- текущее положение;
- набор тестовых позиций:
  - `0%`
  - `25%`
  - `50%`
  - `75%`
  - `100%`
- ручной ползунок или numeric input для задания произвольной позиции;
- кнопка `Переместить`;
- кнопка `Вернуть в нейтраль`.

#### UX-акценты

- показывать целевую и фактическую позицию;
- запрещать спам-команды, пока привод не закончил предыдущее движение;
- рядом короткий hint, что именно физически должен увидеть оператор.

#### Backend-потребности

Вероятнее всего понадобятся явные test-endpoints, если их ещё нет:

- `GET /api/servo/status`
- `POST /api/servo/move`
- `POST /api/servo/stop` или `POST /api/servo/home`

### 4. Группа `Термометры`

#### Назначение

Показать все температурные датчики в одном месте и дать быстрый доступ к существующей калибровке.

#### Что должно быть внутри

- список всех датчиков;
- текущее значение;
- валидность;
- возраст последнего обновления;
- адрес датчика;
- визуальная индикация:
  - `OK`
  - `offline`
  - `stale`

#### Что переносим из текущего интерфейса

- сканирование датчиков;
- offset calibration;
- reference calibration.

#### Рекомендуемое улучшение

Разделить датчики на смысловые подгруппы:

- `Процесс`
  - куб
  - царга низ
  - царга верх
  - дефлегматор
  - ТСА
- `Охлаждение`
  - вода вход
  - вода выход

Это сделает раздел гораздо понятнее, чем список "как нашли — так и вывели".

#### Backend-потребности

База уже есть:

- `GET /api/calibration`
- `GET /api/calibration/scan`
- `POST /api/calibration/temp`

Новых API на первом этапе не требуется.

### 5. Группа `ТЭН`

#### Назначение

Безопасная сервисная проверка ТЭНа на заданной мощности без запуска рабочего режима.

#### Что должно быть внутри

- текущая мощность;
- заданная мощность;
- поле ввода мощности;
- главная кнопка `Запустить тест ТЭНа`;
- после запуска — `Остановить ТЭН`.

#### Обязательная логика запуска

После нажатия `Запустить тест ТЭНа` всегда открывать модальное предупреждение:

- крупный warning;
- текст в духе:
  - `Убедитесь, что ТЭН полностью погружен в жидкость. Сухой запуск опасен и может вывести оборудование из строя.`;
- чекбокс подтверждения;
- только после явного подтверждения разрешать включение.

#### Safety-ограничения

Не разрешать запускать тест ТЭНа, если:

- активен процесс;
- сработала авария;
- demo mode;
- нет подтверждения пользователя;
- есть признаки опасного состояния.

#### UX-акценты

- использовать danger-цветовую схему;
- текущую мощность показывать крупно;
- рядом выводить несколько связанных величин:
  - напряжение;
  - ток;
  - оценка реальной мощности, если доступна.

#### Backend-потребности

С высокой вероятностью нужны отдельные test-endpoints:

- `POST /api/heater/test/start`
- `POST /api/heater/test/stop`
- `GET /api/heater/test/status`

Если direct-control уже существует внутренне, всё равно лучше вынести отдельный безопасный test-contract, а не навешивать UI прямо на рабочий драйвер.

### 6. Группа `Датчик давления`

#### Назначение

Проверка того, что датчик живой и реагирует на изменение давления.

#### Что должно быть внутри

- текущее давление;
- baseline/начальное значение;
- индикатор изменения;
- инструкция:
  - `Слегка дуньте в линию датчика и смотрите, меняется ли значение`.

#### Основная механика теста

- кнопка `Начать тест`;
- после старта фиксируется baseline;
- в течение окна наблюдения:
  - если значения меняются заметно, карточка подсвечивается зелёным;
  - если изменений нет, остаётся нейтральной или подсвечивается warning-цветом;
- кнопка `Сбросить тест`.

#### Полезные индикаторы

- текущее значение;
- delta от baseline;
- min/max за тест;
- скорость изменения.

#### Backend-потребности

Если текущее давление уже есть в live status, отдельного API для первого этапа не нужно. Достаточно фронтовой логики поверх текущего статуса.

### 7. Группа `Ареометр`

#### Назначение

Подготовить место для будущей диагностики датчика ареометра без преждевременной жёсткой реализации.

#### Что должно быть внутри на первом этапе

- заглушка-карточка;
- текущие доступные значения:
  - `ABV`
  - `valid`
  - сырой сигнал/давление, если есть;
- статус:
  - `Поддержка тестирования в разработке`;
- текст-пояснение, что позже здесь появится интерактивная проверка по живому отклику.

#### Что не делать сейчас

- не придумывать фиктивный сценарий тестирования;
- не делать небезопасных псевдо-кнопок без реальной backend-логики.

### 8. Дополнительная группа `Питание и силовая диагностика`

Это не было прямо запрошено, но логически полезно и почти наверняка пригодится.

#### Назначение

Помочь быстро понять, видит ли система нормальное питание и силовую часть.

#### Что должно быть внутри

- напряжение;
- ток;
- мощность;
- состояние силового канала, если доступно;
- health-индикаторы по связанным датчикам.

#### Почему это полезно

Когда оператор тестирует насос, ТЭН или клапаны, ему важно тут же видеть, есть ли электрический отклик, а не ходить в другие вкладки.

## Рекомендации по визуальной компоновке

### 1. Не делать сплошную длинную "простыню"

Рекомендуемый layout:

- сверху компактная панель состояния и safety;
- ниже grid из крупных групп;
- внутри группы:
  - summary view;
  - expandable details.

### 2. Приоритет визуального порядка

Расположить группы так:

1. `Насос`
2. `Клапаны`
3. `Сервопривод`
4. `ТЭН`
5. `Термометры`
6. `Датчик давления`
7. `Ареометр`
8. `Питание и силовая диагностика`

Логика порядка:

- сначала исполнительные устройства;
- потом датчики процесса;
- потом вспомогательная диагностика.

### 3. Не прятать ключевые показания

На карточке каждого узла должны быть видны без раскрытия:

- текущее состояние;
- главное измерение;
- есть ли ошибка;
- готов ли узел к тесту.

## Safety-политика для реализации

### Общие блокировки

Нужен единый guard-layer для ручных тестов:

- блокировать, если активен процесс;
- блокировать при аварии;
- блокировать конфликтующие тесты;
- блокировать физические действия в demo mode;
- логировать операторские test-actions в журнал.

### Отдельные опасные тесты

Повышенные подтверждения нужны для:

- ТЭНа;
- любых движений, которые могут реально открыть поток/слив;
- возможно, сервопривода, если он влияет на продуктовый тракт.

### Глобальная кнопка

В `Тестирование` обязательно нужна кнопка:

- `Остановить все тесты`

Она должна:

- выключать насос;
- выключать ТЭН;
- останавливать активные servo/valve test-actions;
- очищать локальные test-сессии интерфейса.

## Backend-контракты: что уже есть и что нужно будет добавить

### Уже существует и должно быть переиспользовано

- pump start/stop/status/diag;
- pump calibration;
- temp scan/calibration;
- live status с температурой, давлением, ареометром;
- demo mode status.

### Понадобится добавить или нормализовать

- клапаны:
  - статус;
  - open/close;
  - возможно pulse/test;
- сервопривод:
  - status;
  - move to position;
  - home/neutral;
- ТЭН:
  - безопасный test start/stop/status;
- общий test supervisor:
  - список активных тестов;
  - emergency stop all;
  - test availability reason.

## Предлагаемое поведение журналирования

Все ручные тестовые действия полезно логировать как отдельные operator events:

- старт теста насоса;
- стоп теста насоса;
- открытие/закрытие клапана;
- движение сервопривода;
- подтверждение запуска ТЭНа;
- успешный тест датчика давления;
- отмена теста.

Это поможет потом понимать:

- что именно делал оператор;
- почему железо было включено;
- не совпадает ли это по времени с ошибками или авариями.

## Этапы внедрения

### Этап 1. Перестройка структуры `Оборудование`

- ввести локальную поднавигацию:
  - `Параметры`
  - `Калибровка`
  - `Тестирование`;
- разнести текущие карточки по правильным подпунктам;
- сохранить все уже работающие сценарии без регрессий.

### Этап 2. Запуск первой полезной версии `Тестирование`

- верхняя сервисная панель;
- группа `Насос`;
- группа `Термометры`;
- группа `Датчик давления` как frontend-driven diagnostic.

Это даст быстрый полезный результат с минимальным риском.

### Этап 3. Тесты исполнительных устройств

- `Клапаны`;
- `Сервопривод`;
- `ТЭН` с обязательным подтверждением.

На этом этапе нужно особое внимание к safety interlocks.

### Этап 4. Заглушки и расширенная диагностика

- `Ареометр` как planned placeholder;
- `Питание и силовая диагностика`;
- общий `Остановить все тесты`;
- журналирование operator test-actions.

### Этап 5. Полировка UX

- единый визуальный язык карточек;
- цветовые статусы;
- компактные mobile-friendly раскладки;
- понятные подсказки и warning-text;
- приведение сообщений и labels к единому стилю.

## Критерии готовности

Раздел можно считать готовым к production-использованию, когда:

- `Оборудование` логически разделено на `Параметры`, `Калибровка`, `Тестирование`;
- все основные физические узлы имеют собственные test-группы;
- demo mode гарантированно не управляет железом;
- опасные узлы имеют подтверждение и safety-blocks;
- оператор может протестировать насос, клапаны, сервопривод, ТЭН, термометры и датчик давления без переходов по разным вкладкам;
- ареометр имеет корректную заглушку, а не недоделанную псевдо-функцию;
- доступна единая кнопка `Остановить все тесты`;
- все test-actions журналируются.

## Что важно не сломать

- текущую калибровку насоса;
- текущую калибровку термометров;
- существующий demo mode;
- существующие safety-ограничения;
- текущие рабочие режимы и их API.

## Открытые вопросы перед реализацией

Эти вопросы не мешают начать работу, но их полезно подтвердить до coding-phase:

1. Финальный список клапанов, которые должны быть видны в UI поштучно.
2. Какие именно сценарии движения нужны для сервопривода, кроме позиционирования по процентам.
3. Нужен ли отдельный ручной тест охлаждающей воды как самостоятельная группа, или достаточно термометров и клапанов.
4. Нужно ли скрывать опасные тесты за режимом `Расширенный доступ`, или достаточно модальных подтверждений.

## Рекомендация по старту реализации

Лучший первый coding-pass:

1. сначала сделать внутреннюю поднавигацию `Параметры / Калибровка / Тестирование`;
2. затем вынести в `Тестирование` насос и термометры;
3. после этого добавить pressure-test;
4. и только потом включать силовые тесты клапанов, сервопривода и ТЭНа.

Так мы быстро получим полезный сервисный раздел без лишнего риска и без большого одноразового рефакторинга.
