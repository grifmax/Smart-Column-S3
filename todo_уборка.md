## Цель и границы

Документ фиксирует **результаты инвентаризации** кода (2.6.0) и план его
уборки. Это не план новых возможностей: ни одна задача здесь не меняет
поведение прибора. Всё, что меняет поведение, идёт отдельными задачами вне
этого документа.

Три направления:

- **мёртвый код** — то, что не компилируется в образ или не вызывается никем;
- **дублирование** — одна и та же логика в нескольких местах;
- **покрытие тестами** — чтобы уборка и последующие правки шли под защитой.

### Правило идентификаторов задач

Каждый чекбокс имеет неизменяемый ID вида `C-###`. На него ссылаются в
обсуждениях, коммитах и отчётах: `C-004 готово`, `C-021 ожидает стендовой
проверки`. При добавлении задачи назначать следующий свободный номер, уже
существующие не перенумеровывать.

Статусы: `[ ]` — не начато, `[~]` — в работе, `[x]` — принято. Подзадачи без
чекбокса — пояснение или критерий приёмки для родительской задачи.

Префикс `C-` не пересекается с `D-###` из `todo-Distiller.md`: там задачи
развития, здесь — гигиена кода.

### Методика измерения

Все цифры получены разбором дерева `src/`, а не на глаз:

- строки кода — построчный разбор с исключением комментариев и пустых строк;
- мёртвые функции — поиск определений верхнего уровня, затем подсчёт вхождений
  идентификатора по всему `src/`; функция считается мёртвой, если её имя
  встречается только там, где она определена;
- дублирование тел — нормализация пробелов и сравнение по SHA-1;
- размер функций — подсчёт по балансу скобок от сигнатуры.

Ограничение методики: мёртвость определяется по тексту. Функция, вызываемая
только через указатель или из макроса, может быть помечена ошибочно — поэтому
перед удалением каждой группы идёт ручная проверка (см. критерии приёмки).

  значениями — сверить полный дамп `/api/settings/*` и `/api/calibration`
  до и после.

## Этап 3 — покрытие тестами

Ценность высокая, риск нулевой. Из 24 заголовков `*_logic.h` тестами покрыты
**два**: `rate_estimator` и `water_test`. Остальные 22 — включая шлюз команд,
логику отбора, калибровку насоса и восстановление после сбоя — не проверяются
вообще. Вся защита держится на внимательном чтении кода.

### C-019 Включить предупреждения компилятора

- [ ] **C-019** Добавить `-Wall -Wextra` в `build_flags` в
  `platformio.ini`. Сейчас предупреждения выключены полностью.

  Критерий приёмки: собрать, получить список предупреждений, разобрать по
  категориям. Не включать `-Werror` сразу: сначала устранить существующие
  предупреждения, иначе сборка встанет.

### C-020 Тесты для power_command_gateway_logic

- [ ] **C-020** Покрыть `src/control/power_command_gateway_logic.h`:
  приоритеты владельцев (`FSM` против `SERVICE` против `MANUAL`),
  отклонение команд при защёлкнутой аварии, `ownerFloorAllows`,
  коалесцирование остановов.

  Почему это первое: вся безопасность выходов идёт через шлюз, и именно здесь
  недавно нашлась ошибка с закрытием воды при аварии.

### C-021 Тесты для pump_calibration_logic

- [ ] **C-021** Покрыть `src/control/pump_calibration_logic.h`: оценка замера,
  защита от скачка коэффициента больше чем в 2 и 4 раза, отказ при
  нулевом объёме, корректность при невалидном счётчике шагов.

  Почему важно: здесь мы уже поймали реальный дефект — калибровка,
  снятая на одной разрядности микрошагов, переставала биться при смене.

### C-022 Тесты для rect_takeoff_logic

- [ ] **C-022** Покрыть `src/control/rect_takeoff_logic.h`: окна
  периодического отбора (`SR_RATIO`, `AUTONOMOUS`), расчёт скважности,

  числе.

  Почему важно: после C-010 эта логика станет общей для авто- и ручной
  ректификации — ошибка ударит по обоим режимам сразу.

### C-023 Тесты для process_resume_logic и safety_policy

- [ ] **C-023** Покрыть `src/control/process_resume_logic.h` (восстановление
  после сбоя питания на разных фазах) и `src/control/v2/safety_policy.h`

  Почему важно: восстановление после сбоя — сценарий, который нельзя

### C-024 Тесты для sensor_freshness_logic

- [ ] **C-024** Покрыть `src/control/sensor_freshness_logic.h`: границы

  Почему важно: именно здесь решается, когда датчик считается отвалившимся, и
  именно по этой логике было три ложных останова на переходе «головы → тело».

## Чего не трогаем

Зафиксировано, чтобы к этим пунктам не возвращались:

- **`drivers/display.cpp` целиком** (8 421 строка). Разбиение TFT-слоя на
  модули — работа на неделю с высоким риском сломать экран, выигрыш только в
  удобстве. Локальная чистка мёртвого (C-002) достаточна.
- **`SystemState g_state` как глобал.** Перевод на инъекцию зависимостей
  затронет 175 файлов. Не окупается.
- **`hmi2_core.inc`** (1 933 строки, вклеивается через `#include` посреди
  `display.cpp`). Вынос в отдельный модуль потребует передать всё состояние
  экрана явно — переделка сопоставима с переписыванием TFT.
- **Разделение `types.h`** (1 041 строка). Он тянется в 34 файла; дробление
  ускорит сборку, но потребует правки всех включений.

## Порядок выполнения

```text
Этап 0 (мёртвый код)        →  C-001 … C-007   минус ~4 000 строк, поведение не меняется
    ↓

    ↓

```

Этап 3 идёт до этапа 1 не случайно: `isTakeoffWindowOpen` (C-010) и
`normalizeRectFractions` (C-009) проще сначала покрыть тестом в текущем виде,
а затем сводить копии, сверяя результат.

## Критерии готовности этапа

**Этап 0 закрыт**, когда:

- сборка успешна, `firmware.bin` после C-001 побайтово равен образу до правки;
- 128 нативных тестов зелёные;
- `grep` не находит ни одного из удалённых идентификаторов;
- `#if 0` в `src/` не осталось.

**Этап 1 закрыт**, когда:

- каждая сведённая функция существует ровно в одном месте;
- ответы `/api/status`, `/api/calibration` и облака не изменились по ключам.

**Этап 2 закрыт**, когда:

- множества ключей состояния в трёх потребителях совпадают;
- список путей облака совпадает со списком локальных `/api/*`.

**Этап 3 закрыт**, когда:

- `*_logic.h` без тестов не осталось, либо отсутствие теста обосновано
  записью в этом документе;
- сборка проходит с `-Wall -Wextra` без новых предупреждений.
