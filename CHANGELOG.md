# Журнал изменений

Все значимые изменения в этом проекте будут документированы в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
и этот проект придерживается [Semantic Versioning](https://semver.org/lang/ru/).

---

## [2.4.79] - 2026-07-17

### Added
- В авто-ректификации добавлен выключенный по умолчанию контур мощности по давлению: выше рабочего коридора мощность плавно снижается, на safety-пороге нагрев отключается. Контур принимает только валидную монотонную калибровку и устойчивый свежий сигнал; при отказе датчика сохраняется мощность профиля и выдаётся предупреждение в preflight. Параметры доступны через NVS, API и UI. (codex)

## [2.4.78] - 2026-07-17

### Added
- В дистилляции появился выключенный по умолчанию контур температуры дефлегматора: он плавно меняет мощность в заданных границах, умеет завершать отбор по тайм-ауту и сохраняет настройки в NVS. UI и API передают единый контракт контура; завершение по температуре куба и объёму сохранено. (codex)

## [2.4.77] - 2026-07-17

### Fixed
- Cloud API профилей теперь обновляет `fractionProgram` через общий parser, а cloud status публикует тот же profile/runtime контракт программы фракций, что и local API. (codex)

## [2.4.76] - 2026-07-17

### Changed
- Runtime-карточка затора теперь показывает цель, текущую температуру, остаток и действие оператора активного типизированного шага. Зерновые, мучные и пивные сценарии закреплены как шаблоны единой MASHING FSM. (codex)

## [2.4.75] - 2026-07-17

### Changed
- Live status НБК показывает расход подачи (заданный/скорректированный/фактический), объём браги и ограничивающий фактор. Подача закреплена за штатным `Pump` в физических мл/ч, без переноса аппаратных масок сторонних контроллеров. (codex)

## [2.4.74] - 2026-07-17

### Changed
- НБК теперь безопасно удерживает подачу после ограничений до 30 секунд устойчивых температуры/давления, поддерживает завершение по заданному объёму браги и использует давление как защитный ограничитель, а не основной контур расхода. (codex)

## [2.4.73] - 2026-07-17

### Changed
- НБК закрепляет текущий калиброванный перистальтический насос как backend подачи браги; добавлена выключенная по умолчанию медленная коррекция расхода по температуре верха колонны. (codex)

## [2.4.72] - 2026-07-17

### Changed
- НБК получила отдельную фазу `FEED_RAMP`: после стабилизации подача браги на текущем перистальтическом насосе за 60 секунд плавно выходит на заданный расход и лишь затем переходит в `WORKING`. (codex)

## [2.4.71] - 2026-07-17

### Changed
- Ферментация переведена на единый цикл PREPARE/HEATING/COOLING/FERMENTATION/COMPLETED с активным охлаждением, минимальным временем клапана, общим температурным коридором и защитой пены. (codex)

## [2.4.69] - 2026-07-17

### Changed
- Шаг кипячения затора теперь отправляет три уведомления о внесении хмеля от момента подтверждённого кипения: в начале, середине и за пять минут до завершения. (codex)

## [2.4.68] - 2026-07-17

### Changed
- MASHING получил безопасное управление мешалкой по шагам, защиту верхнего уровня/пены через A2, рекомендацию ручного перехода к ферментации после охлаждения и явный запрет использовать насос отбора для неявного автодозирования дрожжей. (codex)

## [2.4.67] - 2026-07-17

### Changed
- В MASHING добавлены подтверждение кипения по TSA с резервом по температуре куба и безопасным таймаутом, отдельная максимальная мощность разваривания и импульсное охлаждение водой с мешалкой. (codex)

## [2.4.66] - 2026-07-17

### Changed
- Для шага `operator_wait` добавлены защищённое действие «Подтвердить шаг» и `POST /api/mashing/next`. Переход доступен только в ожидающей паузе и записывается в v2 history с причиной `RC_MANUAL_OPERATOR_SWITCH`. (codex)

## [2.4.65] - 2026-07-17

### Changed
- Нулевая длительность шага затора теперь означает явное действие оператора: UI сериализует такой шаг как `operator_wait`, а MASHING безопасно ждёт команды «Продолжить». (codex)

## [2.4.64] - 2026-07-17

### Changed
- В панель затора добавлены готовые шаблоны: солодовый профиль, зерновой затор с развариванием, мучной затор без разваривания и охлаждение перед брожением. Шаблоны используют единую типизированную последовательность шагов. (codex)

## [2.4.63] - 2026-07-17

### Changed
- MASHING FSM теперь исполняет типы `heat`, `hold`, `operator_wait`, `boil`, `cool`, `stir` и `finish` в едином сценарии: ожидание оператора ставит процесс на безопасную паузу, охлаждение выключает нагрев и открывает воду, а остальные температурные шаги используют существующий контроль допуска и выдержки. (codex)

## [2.4.62] - 2026-07-17

### Changed
- `MashProfile` и профильный API переведены на типизированные технологические шаги (`heat_hold`, `heat`, `hold`, `operator_wait`, `boil`, `cool`, `stir`, `finish`) с обратной совместимостью температурных пауз. Неисполняемые до следующего этапа типы безопасно отменяют запуск вместо неявной трактовки как нагрев. (codex)

## [2.4.61] - 2026-07-17

### Changed
- Зафиксирован и применён порядок совместной работы BODY: safety/пауза → уровень и смена ёмкости → завершение тела по PB/условию → CHIM → флегмовый режим → backend. Переход к хвостам теперь останавливает текущий отбор в той же итерации, а НДРФ документально оставлен не реализуемым дубликатом ректификации. (codex)

## [2.4.60] - 2026-07-17

### Changed
- Общий датчик уровня ADS1115 A2 теперь также защищает текущую ёмкость голов: при переливе отбор останавливается и ждёт смены тары/переноса датчика и снятия сигнала. В UI датчик назван датчиком активной приёмной ёмкости. (codex)

## [2.4.59] - 2026-07-17

### Changed
- Датчик уровня ADS1115 A2 в ректификации теперь относится к активной ёмкости тела: срабатывание выключает общий тракт и ставит процесс на паузу, а возобновление возможно только после смены тары/переноса датчика и снятия сигнала. Состояние датчика активной ёмкости добавлено в `/api/status`. (codex)

## [2.4.57] - 2026-07-15

### Changed
- Завершён этап `2.2` исполнительного тракта для фракционной дистилляции: дистилляционный handler переведён на общий `RectTakeoff` coordinator, поэтому смена маршрута и запуск отбора теперь проходят через единый безопасный сценарий `pump off -> route -> settle -> pump on`, как и в ректификации. (codex)
- `/api/status` расширен runtime-полями фракционной программы: Web UI и внешние клиенты теперь получают имя шага, целевой и фактический маршрут, фактическую скорость отбора, накопленный объём текущей фракции и ожидаемый критерий завершения. (codex)
- В runtime-карточке дистилляции добавлены операторские действия `Пауза`, `Продолжить`, `Следующая фракция` и `Остановить`, а ручной переход на следующий шаг вынесен в отдельный web action `requestFractionProgramNext()` поверх `POST /api/fraction-program/next`. (codex)

## [2.4.55] - 2026-07-14

### Fixed
- Исправлен регресс интерфейса авторектификации: показания на схеме процесса снова читаемы в тёмной теме, потому что числовые индикаторы больше не перекрашиваются в светлый цвет поверх белых плашек. (codex)
- Исправлены битые строки в карточке прогресса авторектификации: подпись фазы, маршрута и активной фракции снова отображается нормальным русским текстом без кракозябр. (codex)
- Полноэкранный операторский экран авторектификации снова держит верхние карточки в одном вертикальном потоке: блоки "Сейчас важно" и "Прогресс авто-ректификации" больше не раскладываются в две колонки на широком экране. (codex)

## [2.4.54] - 2026-07-14

### Changed
- В обычном окне запуска авторектификации блок CHIM/PB заменён на понятную сводку "Автокоррекция скорости отбора": интерфейс теперь показывает расчётный профиль, температурную и накопительную коррекцию, стартовую поправку, минимум отбора и логику завершения тела, а скрытые служебные поля синхронизируются программно из текущего режима отбора. Экспертные параметры профиля при этом переименованы в более понятные русские формулировки без изменения совместимого payload. (codex)

## [2.4.53] - 2026-07-05

### Changed
- Именование route-registration функций унифицировано по всему `src/interface/api/`: верхнеуровневые модули теперь используют шаблон `register...ApiRoutes`, а settings-подмодули приведены к тому же стилю. Это упрощает навигацию по API-слою и снижает путаницу между публичными API-регистраторами и внутренними settings-регистраторами. (codex)
- Добавлен базовый host-side test harness `native_json_tests` с общими JSON assertion helper-ами и первым smoke-тестом, чтобы дальше можно было покрывать JSON builders unit-level проверками без прошивки на ESP32. (codex)

## [2.4.52] - 2026-07-05

### Changed
- В `cloud_tunnel.cpp` убраны дубли базовых helper-функций, которые уже живут в `webserver_shared`: cloud-слой теперь переиспользует общие реализации для security apply, topology support, clamps, mode parsing, booster override и V2/alarm JSON fillers, а локально оставляет только cloud-специфичные обёртки и payload-расширения. Это уменьшает расхождение между локальным Web API и облачным туннелем и упрощает дальнейшую поддержку рефакторинга. (codex)

## [2.4.51] - 2026-07-05

### Changed
- В `webserver_shared` добавлены базовые response helpers `sendJsonSuccess(...)` и `sendJsonError(...)`, и на них переведены однотипные JSON-ответы в `settings_*` и части `api_wifi.cpp`. Это сокращает дублирование ручного `request->send(..., "application/json", ...)` без изменения URL и с сохранением прежних payload-форматов там, где они были нестандартными. (codex)

## [2.4.50] - 2026-07-05

- Рефакторинг `api_settings.cpp`: settings-роуты и связанные runtime/system handlers разнесены по внутренним подмодулям `settings_equipment`, `settings_thresholds`, `settings_modes`, `settings_mqtt`, `settings_runtime` и `settings_system`, а `registerSettingsRoutes(...)` оставлен тонким координатором. URL, payload и поведение API при этом не менялись. (codex)

## [2.4.49] - 2026-07-05

### Fixed
- Исправлен live-таймаут ответа у `POST /api/wifi/connect`: переподключение Wi-Fi больше не стартует синхронно прямо в HTTP handler через `delay()` и мгновенный `WiFi.begin()`, а откладывается в короткую FreeRTOS-задачу после отправки ответа. Это должно вернуть стабильный JSON-ответ клиенту и убрать подвисание Web UI на ручном connect. (codex)

## [2.4.48] - 2026-07-05

### Fixed
- Исправлен live-конфликт Wi-Fi POST-маршрутов в `ESPAsyncWebServer`: `POST /api/wifi/profile/delete` и `POST /api/wifi/profile/reorder` раньше перехватывались более общим `POST /api/wifi/profile` из-за prefix-match, поэтому delete/reorder фактически превращались в upsert. Все конфликтующие Wi-Fi POST endpoints переведены на anchored exact regex routes, и delete/reorder/connect снова должны выполнять именно свою логику. (codex)

## [2.4.47] - 2026-07-05

### Fixed
- Для `ESPAsyncWebServer` вынесен общий helper разбора chunked JSON body в `webserver_shared`, и на него переведены POST-ручки `process`, `pump`, `wifi`, `safety`, `calibration`, `testing` и `settings`. Это убирает скрытую зависимость от single-chunk payload и должно стабилизировать большие запросы из Web UI, включая настройки, preflight, cloud config и сервисные действия. (codex)

## [2.4.46] - 2026-07-05

### Fixed
- Исправлен конфликт GET-маршрутов калибровки в `ESPAsyncWebServer`: `/api/calibration`, `/api/calibration/scan` и `/api/calibration/scan/raw` теперь зарегистрированы как anchored regex routes, поэтому live-контроллер больше не подменяет scan-ответы общим calibration snapshot по prefix-match. Это снижает давление на память при сериализации `saveProcessHistory(...)` и должно восстановить `POST /api/history/demo` на live-контроллере. (codex)

## [2.4.41] - 2026-07-04
