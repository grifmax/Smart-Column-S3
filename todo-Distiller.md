# TODO: полезные заимствования из `Manual_Distiller6_r1.pdf`

## Цель и границы

Источник сравнения — руководство Distiller+ для прошивки 6.xx, 82 страницы:
`Manual_Distiller6_r1.pdf`. Этот документ — не план копирования чужой
прошивки или её распиновки. Он фиксирует только то, что для Smart-Column S3:

- добавляет новую полезную возможность;
- делает имеющийся сценарий заметно проще на локальном TFT;
- не дублирует уже более сильную реализацию SC-S3.

Главная задача — перенести на TFT понятную модель меню Distiller+: выбор
режима → настройки/безопасность → запуск → экран процесса → сервис. Меню
должно содержать только поддерживаемые SC-S3 режимы, датчики, исполнительные
устройства и настройки; названия, аппаратные выходы и логика Distiller+
не копируются буквально.

### Правило идентификаторов задач

Каждый чекбокс имеет неизменяемый ID вида `D-###`. На него нужно ссылаться в
обсуждениях, коммитах, issue и отчётах о проверке: например, `D-018 готово`,
`D-031 заблокирована hardware profile`. При добавлении новой задачи назначать
следующий свободный номер, а не перенумеровывать уже существующие пункты.

Статусы: `[ ]` — не начато, `[~]` — в работе, `[x]` — принято. Подзадачи без
чекбокса — пояснение или критерий для родительской задачи, а не самостоятельный
элемент плана.

## P0 — новое TFT-меню: полностью заменить текущую информационную архитектуру

### Принцип

Оставить сильные стороны текущего интерфейса — частичную перерисовку,
RU/EN, live-метрики и блокировки редактирования — но **полностью заменить
текущий HMI**, включая нижние вкладки, старые root-экраны и их layout. Это не
постепенная перестановка карточек: после миграции у оператора остаётся один
новый цельный интерфейс. В `IDLE` главный экран — выбор процесса; в активном
процессе — экран текущего процесса с одинаковым контекстным меню.

Постоянный верхний status bar обязан показывать сетевое состояние и адрес
подключения к устройству. Формат зависит от состояния:

```text
STA подключён:  Wi-Fi • 192.168.1.42
Точка доступа:  AP • 192.168.4.1
Подключение:    Wi-Fi • подключение…
Нет сети:        Wi-Fi • нет IP
```

IP не является заменой safety-индикации: активная критическая авария имеет
приоритет в цвете/status bar, но IP остаётся доступным в строке или во
всплывающей карточке по тапу. Адрес обновляется без полного redraw при смене
DHCP, reconnect и AP fallback.

```text
ГЛАВНОЕ МЕНЮ
├─ Монитор / текущий процесс
│  ├─ Температуры, давление, мощность, насос, клапаны, тревоги
│  ├─ Текущий шаг / фракция / причина ограничения
│  ├─ Пауза · Продолжить · Стоп
│  └─ События и активные рекомендации
├─ Выбрать и подготовить режим
│  ├─ Авто-ректификация
│  ├─ Ручная ректификация
│  ├─ Дистилляция
│  ├─ Затирание
│  ├─ Hold / пастеризация
│  ├─ НБК
│  └─ Брожение
├─ Настройки автоматики
│  ├─ Оборудование и охлаждение
│  ├─ Датчики и калибровки
│  ├─ Safety
│  ├─ Экран, звук и язык
│  └─ Статус подключения и версии
└─ Сервис
   ├─ Проверка оборудования
   ├─ Ручное управление
   ├─ Диагностика датчиков и модулей
   └─ Краткий журнал аварий
```

```text
Общий chrome всех экранов
├─ Верхняя строка: режим / safety-индикатор / Wi-Fi-состояние / IP
├─ Рабочая область: содержимое текущего пункта меню
└─ Нижняя строка: контекстные действия и Back/Home; старые четыре вкладки не сохраняются
```

Для каждого выбранного режима открыть одинаковую подготовительную карточку:

```text
<РЕЖИМ>
├─ Профиль / пресет
├─ Основные параметры
├─ Технологические параметры       # только относящиеся к режиму
├─ Охлаждение и исполнительные узлы
├─ Безопасность
├─ Pre-flight
└─ Старт
```

Во время процесса те же пункты доступны из меню `Процесс`, но каждый имеет
явную политику: `только просмотр`, `можно менять на ходу` или `только после
паузы`. Safety-пороги, калибровки и аппаратную конфигурацию во время
автопроцесса не редактировать.

### Контракт экранов и переходов

| Экран | Доступ | Вход | Выход / критичное действие |
| --- | --- | --- | --- |
| `MODE_PICKER` | Только `IDLE` | Главный экран | Выбор режима открывает `MODE_SETUP`, но ничего не запускает |
| `MODE_SETUP` | `IDLE` | Выбор режима или возврат из Pre-flight | Любое изменение остаётся черновиком до явного `Сохранить`; `Старт` всегда ведёт в `PREFLIGHT` |
| `PREFLIGHT` | `IDLE` | Только из `MODE_SETUP` | Запрос к той же backend-проверке, что и Web UI; критический блок запрещает старт |
| `PROCESS_MONITOR` | Активный режим / пауза | Автоматически после старта | Пауза, продолжение и стоп требуют тех же условий, что `FSM`/API |
| `PROCESS_PARAMS` | Активный режим / пауза | Меню процесса | Поля определяются allowlist конкретного режима; запрещённое поле видно, но заблокировано с причиной |
| `SAFETY_VIEW` | Всегда | Главное или меню процесса | Acknowledge/reset доступны только при текущих safety conditions |
| `SERVICE_TEST` | `IDLE`; из процесса — после сервисной паузы | Сервис | Выход всегда отправляет `stop-all` и предлагает безопасное возвращение в FSM |
| `CALIBRATION_WIZARD` | Только `IDLE` | Настройки / сервис | Отмена не пишет частичный результат; сохранение валидирует все введённые точки |

Общее правило навигации: `Назад` не отменяет уже отправленную силовую команду.
Для любого мастера с работающим приводом на экране всегда есть заметная кнопка
`Стоп`, а выход требует либо его автоматического выполнения, либо явного
подтверждения безопасного состояния.

### Матрица параметров режима на TFT

Это состав экранов, который должен заменить нынешние лишь частичные
`RECT_PARAMS` и `DIST_PARAMS`. Сложные редакторы списков оставляют один
короткий обзор и кнопку перехода в Web UI, но не скрывают состояние процесса.

| Режим | Экран «Основное» | Экран «Технология» | Runtime-изменения |
| --- | --- | --- | --- |
| Авто-ректификация | профиль, сырьё, объём, ABV, backend отбора | головы/тело/хвосты, стабилизация, продувка, барокоррекция, фракционник, тара | По умолчанию просмотр; только отдельно одобренные безопасные параметры |
| Ручная ректификация | мощность, скорость, цели фракций | маршруты и ручные действия | скорость, мощность и цели фракций |
| Дистилляция | мощность, головы, целевой объём, конечная температура | программа фракций, backend, контроль температуры пара | мощность и конечная температура; программа фракций — только в паузе или до старта |
| Затирание | выбранный рецепт/шаги | кипячение, охлаждение, мешалка, ожидания оператора | только текущий шаг и разрешённые его поля |
| Hold / пастеризация | шаги температуры и длительности | охлаждение и мешалка | текущий шаг и разрешённые его поля |
| НБК | мощность, расход, целевой объём | плавный старт, коррекция верха, ограничения | только одобренные расход/мощность после стабилизации |
| Брожение | цель, гистерезис, длительность | нагрев, охлаждение, мешалка, защита от пены | только цель и длительность, если это не создаёт конфликт с phase policy |

Любое runtime-поле должно показывать четыре значения: сохранённая уставка,
текущая эффективная уставка, применённое управляющее воздействие и причину
ограничения. Это сохраняет преимущество SC-S3 перед простым экраном из
руководства.

### Техническая декомпозиция P0

`D-001` должен завершиться единым описанием состояний UI, а не только
перечнем `enum`. Минимальный runtime-контекст:

```text
currentScreen, returnScreen, selectedMode, selectedProfileId,
setupDraft, dirtyMask, processMenuPage, serviceSession, editPermission
```

- `setupDraft` живёт отдельно от `g_settings`: нельзя менять сохранённые
  настройки касанием карточки и затем случайно стартовать с наполовину
  сохранённой конфигурацией.
- `dirtyMask` позволяет показать, что изменено, и предложить `Сохранить /
  Отменить` при переходе назад или к другому режиму.
- `editPermission` вычисляется только из `SystemState`, режима, фазы и
  allowlist — не из видимости кнопки. Это исключает обход ограничений другим
  путём тача.
- Переключение темы, языка и профиля визуального refresh остаётся системным
  быстрым действием, но остальные системные поля должны иметь явную кнопку
  сохранения и read-back из NVS.

`D-006` и `D-007` следует реализовывать через описание поля, а не через
десятки независимых обработчиков тача. Для каждого поля нужны: `id`, заголовок,
единица, min/max/step, read/write callback, условие видимости, policy
редактирования, значение по умолчанию и текст причины блокировки. Это
синхронизирует TFT с API и не создаёт ещё один набор «магических» границ.

Минимальные файлы изменения:

```text
src/drivers/display.cpp        — навигация, рендер и taч-обработчики
src/types.h                    — только если нужен безопасный UI draft/status
src/control/fsm*.cpp           — новые разрешённые runtime setters, не UI-логика
src/interface/webserver_shared.cpp / api_*  — общая валидация, если её ещё нет
docs/TFT_MENU_MATRIX.md        — источник policy доступа и redraw
tools/ui-smoke/tests/          — сценарии тач- и Web-regression
```

TFT не должен вызывать собственные HTTP-эндпоинты к localhost. Он использует
те же доменные setters и валидаторы, которыми пользуются API-обработчики; JSON
остаётся транспортным форматом Web/Cloud, а не вторым контуром управления.

## P0 — сервис с безопасной приостановкой процесса

У Distiller+ проверка оборудования доступна из главного меню и из
`Безопасность` работающего режима. В SC-S3 тестирование уже реализовано в
`/api/testing/*`, но локальный TFT даёт лишь ограниченное ручное управление.
Это нужно упростить, не копируя опасное поведение, при котором работающие
выходы остаются без явного владельца.

- [ ] [D-015] Добавить на TFT `Сервис → Проверка оборудования`: ТЭН, насос, мешалка,
  вода, головы, тело, хвосты, УНО/фракционник, PWM охлаждения и доступные
  датчики — строго по фактической конфигурации платы.
- [ ] [D-016] Перед сервисным тестом из активного процесса создать безопасную
  транзакцию: пауза FSM → остановка конфликтующих узлов → подтверждение
  опасного действия → тест → `Вернуть процесс`. Не оставлять одновременно
  автоматическое и ручное управление одним выходом.
- [ ] [D-017] Добавить экран калибровки исполнительных узлов: пошаговая прокачка и
  измерение насоса вместо одного поля `ml/rev`; при наличии клапанного
  backend — его калибровка через общий `RectTakeoff`, а не отдельную логику.
- [ ] [D-018] Добавить мастера локальной калибровки: назначение/offset DS18B20,
  pressure sensor, ареометр, протечка/уровень. Табличные и редкие экспертные
  настройки могут открываться в Web UI, но TFT должен показывать состояние,
  последнюю калибровку и безопасный переход к мастеру.
- [ ] [D-019] Писать запуск, изменение, отмену и результат каждого сервисного теста
  в системный лог и history; при возврате явно восстановить только разрешённое
  FSM-состояние.

### Протокол сервисной сессии

`D-016` — не просто экран поверх работающего процесса. Нужна короткая
state machine сервисной сессии:

```text
REQUESTED → SAFE_PAUSED → TEST_ACTIVE → STOPPING → RESTORE_READY → CLOSED
                         └────────────→ FAULTED ────────────────┘
```

1. `REQUESTED`: TFT сообщает, какой узел будет тестироваться и почему это
   требует паузы.
2. `SAFE_PAUSED`: `FSM::pause()` завершён, автоматические команды сняты,
   конфликтующие выходы в безопасном состоянии. Если этого добиться нельзя,
   тест не запускается.
3. `TEST_ACTIVE`: один владелец исполнительного узла — сервис. Для ТЭНа,
   насоса, клапана/серво, PWM и мешалки действуют разные лимиты времени и
   обязательные подтверждения.
4. `STOPPING`: `stop-all` выполнен и его фактический результат считан назад.
   Простого изменения UI-флага недостаточно.
5. `RESTORE_READY`: оператор видит, что продолжится, и что останется
   выключенным. Только затем разрешается `FSM::resume()`.
6. `FAULTED`: после safety, потери датчика или таймаута возврат в режим
   запрещён до обычного acknowledge/reset; сервис не может его обойти.

Для опасных тестов нужны минимальные ограничения: ТЭН — мощность, таймаут,
подтверждение; насос — расход и максимальный объём; клапан/servo — маршрут и
таймаут; PWM — duty и длительность; мешалка — безопасная температура. Эти
значения должны быть частью hardware profile, а не константами экрана.

Калибровка насоса (`D-017`) должна иметь последовательность `заполнить
линию → налить тест → ввести фактический объём → показать ошибку → сохранить
или повторить`. В NVS попадает только подтверждённый результат; отмена и
авария оставляют предыдущую калибровку нетронутой.

## P1 — режим «Автоклав»

В руководстве это действительно отдельный процесс (паровой и водяной), а не
просто таймер Hold: есть стерилизация, контролируемый разогрев, охлаждение,
уведомление о температуре выемки и отдельные риски давления. В SC-S3 такого
режима нет.

### Решение до реализации

- [ ] [D-020] Утвердить hardware profile автоклава. Текущие насос отбора и клапан
  охлаждения нельзя неявно считать циркуляционным насосом и сливным клапаном:
  нужны явно назначаемые, безопасные выходы и их реальные limits.
- [ ] [D-021] Утвердить состав первого релиза: `паровой` режим обязателен;
  `водяной с циркуляцией` включать только при наличии отдельного совместимого насоса.
  Не обещать в UI функцию, которую не может выполнить установленное железо.

### Реализация

- [ ] [D-022] Добавить `Mode::AUTOCLAVE`, отдельный handler/FSM, настройки и миграцию
  NVS; не перегружать существующий `HOLD` скрытыми флагами.
- [ ] [D-023] Поддержать фазы: проверка датчиков и подтверждение оператором
  готовности/герметичности → разогрев →
  достижение уставки → стерилизация с таймером только в температурном
  допуске → безопасное охлаждение → ожидание температуры выемки → готово.
- [ ] [D-024] Реализовать только одобренные hardware-profile действия: ограничение
  мощности, управление циркуляцией/сливом, охлаждение и явное отключение
  всего на останове или аварии.
- [ ] [D-025] Добавить отдельный safety contract: обязательные температурный и
  pressure-сенсор, предел давления и скорости его роста, таймаут разогрева,
  отказ датчика, запрет автоперезапуска после потери питания, ручное
  подтверждение перед опасными действиями.
- [ ] [D-026] Вывести автоклав в новый TFT-поток и Web UI, с Pre-flight, историей,
  reason codes и тестами фаз; только затем показать его в главном меню.

### Контракт режима автоклава

Программный pre-flight не может доказать герметичность сосуда. Он проверяет
доступность датчиков, нулевое/безопасное давление, назначение выходов и
готовность safety. Закрытие крышки, клапана и физическую герметичность
подтверждает оператор отдельным чекбоксом перед стартом.

Минимальная модель настроек `AutoclaveSettings` должна содержать:

```text
mode: steam | water
sterilizationTempC, temperatureBandC, sterilizationDurationMin
heatPowerLimitW, optionalHeatRampTargetC, heatTimeoutMin
coolingEnabled, coolingStopTempC
circulationEnabled, drainEnabled, drainDurationSec
pressureMaxMmHg, pressureRiseRateMaxMmHgMin
```

Все поля с `circulation*` и `drain*` неактивны, пока их возможности не
объявлены в выбранном hardware profile. Значение `0` не должно неявно означать
«включить всё время»: для времени и объёма это всегда явно документируется как
`disabled` либо `manual`, в зависимости от поля.

Фазы `AUTOCLAVE_PRECHECK`, `HEATING`, `STERILIZING`, `COOLING`, `READY`,
`FINISH`, `FAULT` обязаны публиковать в status: текущую температуру, уставку,
остаток стерилизации, давление, состояние циркуляции/охлаждения и reason
перехода. Таймер стерилизации идёт только внутри `temperatureBandC`; выход из
допуска останавливает его, а не считает недогрев стерилизацией.

| Событие | Безопасное действие |
| --- | --- |
| Давление выше предела или растёт слишком быстро | Нагрев немедленно 0; далее только заранее определённая safety-последовательность profile, без выдуманного «сброса» через случайный клапан |
| Нет обязательного датчика / потеря свежести | Нагрев 0, режим `FAULT`, требуется диагностировать причину |
| Таймаут разогрева | Нагрев 0, понятное сообщение, без повторного автоматического старта |
| Протечка или аварийный стоп | Все process outputs в fail-safe; охлаждение — строго по безопасной политике конкретной аварии |
| Перезагрузка / потеря питания | Режим не возобновляется сам; нужен новый pre-flight и явный старт оператора |

`D-025` считается закрытой только после review этой таблицы вместе с реальной
схемой выходов: программная логика не может заменить механический
предохранительный клапан, термозащиту и требования к сосуду высокого давления.

## P2 — два независимых контура брожения

Руководство умеет вести две ёмкости с разными целями, временем, нагревом,
охлаждением и мешалками. Текущий `FermentationSettings` SC-S3 описывает один
контур, а текущая плата не предоставляет два независимых набора
исполнительных выходов. Это ценный новый функционал, но не firmware-only
задача.

- [ ] [D-027] Сначала утвердить expansion-board/profile: два датчика температуры,
  два независимых выхода нагрева, два охлаждения и, при необходимости, два
  канала мешалки. Описать failsafe-состояние каждого выхода.
- [ ] [D-028] Заменить единичные настройки на `FermentationZone[2]`, сохранив полную
  обратную совместимость текущего первого контура и его NVS-профилей.
- [ ] [D-029] Для каждой зоны реализовать независимые фазы, hysteresis, minimum
  on/off охлаждения, расписание мешалки, длительность, локальные аварии и
  отдельные записи в status/history.
- [ ] [D-030] На TFT показать две компактные карточки и отдельные настройки зон;
  скрывать вторую зону, если hardware profile её не поддерживает.
- [ ] [D-031] Протестировать параллельный нагрев/охлаждение, отказ одного датчика и
  гарантию, что авария второй зоны не оставляет первую в конфликтующем
  состоянии.

### Контракт двух зон брожения

Нельзя реализовывать две зоны двумя копиями текущих глобальных переменных.
Нужны отдельные конфигурация, runtime и привязка к железу:

```text
FermentationZoneConfig[2]
  enabled, tempSensorRole, targetTempC, hysteresisC, durationHours
  heaterOutput, coolingOutput, stirrerOutput
  coolingMinOnSec, coolingMinOffSec, stirrerSchedule, safety limits

FermentationZoneRuntime[2]
  phase, phaseStartedAt, coolingActive, elapsed, sensorHealth,
  lastReason, activeAlarm, effectiveOutputs
```

Первый hardware profile обязан мигрировать к `zoneCount = 1` без изменения
нынешнего поведения. Вторая карточка и её поля показываются только при
`zoneCount = 2`; это исключает ложное впечатление, что один клапан воды и один
ТЭН могут независимо обслуживать две ёмкости.

Политика аварий должна быть определена до кода:

- глобальная авария питания, протечки, паров или общей безопасности выключает
  оба контура;
- отказ датчика или локальный перегрев зоны выключает только её назначенные
  выходы, сообщает оператору и не даёт незаметно продолжать эту зону;
- продолжение второй здоровой зоны допускается лишь если общие выходы и
  safety не конфликтуют;
- один физический выход нельзя назначить двум зонам. Валидатор hardware
  profile обязан отклонять такую конфигурацию до старта.

History и MQTT/WebSocket должны передавать `zoneIndex`, чтобы графики,
уведомления и Run Advisor не смешивали две ферментации в один процесс.

## P3 — безопасное дозирование фиксированного объёма

В руководстве заявлено дозирование насосом. Для SC-S3 это полезнее как
сервисная операция с калиброванным насосом, а не как ещё один процессный
режим: один и тот же насос уже участвует в отборе и НБК.

- [ ] [D-032] Добавить `Сервис → Дозирование`: маршрут, целевой объём, скорость,
  предварительная прокачка, старт/стоп и отображение фактического объёма.
- [ ] [D-033] Разрешать дозирование только в `IDLE` и только через явно доступный
  маршрут; перед стартом проверять калибровку насоса, датчики/клапаны и
  отсутствие активного процесса.
- [ ] [D-034] На аварии, стопе, потере маршрута или уходе со страницы немедленно
  останавливать насос и закрывать относящиеся клапаны; результат записывать
  в лог.
- [ ] [D-035] Не использовать насос отбора для автодозирования дрожжей или химии без
  отдельного назначенного тракта и явного hardware profile.

### Контракт дозирования

Это конечная операция с собственной сессией, а не `Pump::start()` с таймером
в UI. Состояния: `IDLE → PRIME → READY → DISPENSING → COMPLETED`, а также
`CANCELLED` и `FAULTED`. Для каждого запуска сохранить в логе:

```text
route, requestedVolumeMl, requestedRateMlH, calibrationAtStart,
actualVolumeMl, startedAt, finishedAt, finishReason
```

`PRIME` не входит в целевой объём и требует отдельного подтверждения: оператор
должен видеть, куда сейчас направлена жидкость. Перед `DISPENSING` проверить
пригодность калибровки (ненулевое значение, разумный диапазон, отсутствие
незавершённой калибровочной сессии), доступность маршрута и закрытие
несовместимых клапанов. Нельзя подменять запрошенный маршрут fallback-выходом.

После старта пользователь может только `Стоп`; изменение маршрута, скорости
или цели требует завершить/отменить текущую сессию и создать новую запись.
Это исключает неучтённый объём и облегчает разбор ошибки калибровки.

## Что сознательно не переносим

- Отдельные режимы, которые дублируют наш профильный подход: варианты
  потстилла/дробного перегона и отдельные программы фракций.
- Логику трёх силовых выходов 220 В, сухих контактов ПЧ и шарового крана
  Distiller+. SC-S3 использует свои 12 В/MOSFET, servo, PWM и TMC2209
  backends.
- Устаревшую процедуру прошивки через USBASP/microSD и модель сайта с
  привязочным ключом: у SC-S3 есть OTA, Basic Auth, rate limiting и Cloud
  Tunnel.
- Упрощённые удалённые логи: у SC-S3 уже есть MQTT, history v2, экспорт,
  Web UI и Run Advisor.
- Автоматический рестарт после пропадания питания для нагревательных и
  герметичных процессов. Его допустимость для каждого будущего режима должна
  быть отдельным safety-решением, а не настройкой по умолчанию.

## Порядок работ

```text
D-001 → D-036 → D-037 ─┬→ D-002/D-003/D-004 → D-040 → D-010…D-014
                        ├→ D-005/D-006/D-007/D-008 → D-042…D-045
                        └→ D-015/D-016 → D-017/D-018/D-019

D-048 → D-047 → D-049                                     (общий status bar / IP)

D-020 → D-021 → D-022 → D-023/D-024/D-025 → D-026       (автоклав)
D-027 → D-028 → D-029 → D-030/D-031                      (две зоны)
D-032 → D-033 → D-034/D-035                              (дозирование)
```

1. **Безопасный каркас TFT:** `D-001`, `D-036`–`D-038`, `D-042`, `D-048`.
   Первым видимым элементом нового HMI сделать `D-047` — постоянную строку
   режима, safety и IP. Не менять
   режимы и силовую логику до появления общей модели доступа и владельца
   выходов.
2. **Операторский путь существующих режимов:** `D-002`–`D-014`, `D-039`–
   `D-041`, `D-043`–`D-046`. Результат — все семь существующих режимов можно
   подготовить и безопасно вести с TFT без регрессии Web UI. Завершить этот
   этап `D-049` — стендовой проверкой поведения сетевой строки.
3. **Локальный сервис и калибровка:** `D-015`–`D-019`; выполнять после
   gateway команд, иначе ручной и автоматический владелец выхода могут
   конфликтовать.
4. **Автоклав:** только `D-020`–`D-026` после утверждения реального hardware
   contract и safety review.
5. **Второе брожение:** только `D-027`–`D-031` после появления независимых
   выходов и их profile.
6. **Дозирование:** `D-032`–`D-035` как изолированный сервисный workflow
   после завершения сервисной сессии и калибровки насоса.
