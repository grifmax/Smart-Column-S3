# Инструкции для ИИ-ассистентов (Gemini)

При работе над проектом **Smart-Column S3** необходимо строго соблюдать следующий регламент:

### 1. Сборка и Проверка
- После внесения изменений в код прошивки обязательно запускать сборку: `pio run -e esp32s3`.
- Если затронут фронтенд (папка `src/web/`), обязательно запускать `npm run build` для обновления ассетов в `data/`.
- После успешной сборки и по согласованию с пользователем заливать прошивку в контроллер: `pio run -t upload -e esp32s3 --upload-port COM6` (или актуальный порт).

### 2. Версионирование и Журнал изменений
- При каждом значимом улучшении или исправлении **обязательно** поднимать версию в `src/config.h` (параметр `FIRMWARE_VERSION`).
- Все изменения должны быть задокументированы в `CHANGELOG.md`.
- В конце описания каждого изменения в `CHANGELOG.md` добавлять метку в скобках `(gemini)`, чтобы отличать правки, сделанные этим ИИ.

### 3. Работа с Git
- Каждая новая версия должна сопровождаться коммитом.
- Сообщение коммита должно быть информативным (на английском или русском языке).
- После коммита выполнять `git push`.

### 4. Архитектурные принципы
- Соблюдать модульность (логика режимов в `src/control/modes/`).
- Не использовать блокирующие задержки (`delay`) в основном цикле.
- Все критические параметры безопасности должны проверяться в `src/control/safety.cpp`.
5. Работа с памятью и ресурсами (Особо важно для микроконтроллеров)
Избегать фрагментации кучи: по возможности минимизировать использование класса String (заменять на char arrays или std::string там, где это критично).
При создании новых задач (FreeRTOS Tasks) разумно оценивать размер стека и обязательно использовать vTaskDelay вместо пустых циклов, чтобы отдавать процессорное время другим задачам.
6. Аппаратная часть и Пины
Все назначения пинов (Pinout) должны находиться строго в отдельном конфигурационном файле (например, src/config.h). Запрещено хардкодить номера пинов прямо в файлах логики.
При работе с обработчиками прерываний (ISR) делать код максимально коротким (без блокирующих вызовов) и использовать только функции с суффиксом FromISR.
7. Принципы логирования и отладки
Не использовать сырые Serial.print или Serial.println напрямую в бизнес-логике. Вместо этого использовать макросы логирования проекта (например, LOG_INFO, LOG_ERROR), если они есть, чтобы иметь возможность централизованно управлять уровнем детализации вывода (Debug/Release).
8. Многопоточность и безопасность данных (Concurrency)
Так как ESP32-S3 двухъядерный, при доступе к общим ресурсам (переменным, массивам, аппаратным интерфейсам) из разных задач/ядер обязательно использовать примитивы синхронизации (Mutex / Semaphore).
9. Сетевое взаимодействие (API и WebSocket)
Любое изменение формата обмена данными (JSON, команды через WebSocket / REST) должно синхронно реализовываться и в прошивке (C++), и во фронтенде (JS/TS), чтобы не нарушить связность приложения.
10. Ограничения Файловой системы (LittleFS / SPIFFS)
При сборке фронтенда (npm run build) ассеты (HTML/CSS/JS) должны быть оптимизированы и минифицированы, чтобы гарантированно помещаться в выделенный размер раздела файловой системы на ESP32.
