> Ревизия: 2026-07-15. Источники: HelloDistiller.pdf v5.038.3, код и CHANGELOG.md Smart-Column S3 v2.4.55.
>
> Цель: перенять только полезные процессные решения. Основной тракт отбора SC-S3 — **перистальтический насос + фракционник**. Клапаны остаются бюджетной альтернативой, а не основой архитектуры.

## Обозначения

- [x] [001] Уже реализовано или закрыто существующей архитектурой.
- [ ] [002] Требуется реализовать либо проверить при приёмке.
- P0 — обязательный ближайший этап; P1 — следующий полезный этап; P2 — опциональное развитие.

## Принципы

- [x] [003] Насос — основной исполнитель отбора; скорость задаётся в физических единицах мл/ч.
- [x] [004] В ректификации уже выбирается backend: насос, несколько клапанов или один клапан с фракционником.
- [ ] [005] Новый отбор выполнять через единый координатор: **остановить поток → сменить маршрут → дождаться фракционника → начать отбор**.
- [ ] [006] Клапанный backend использует ту же модель процесса, но имеет ограниченные маршруты и отдельные проверки безопасности.
- [ ] [007] Не копировать «магические» параметры HelloDistiller: датчик, температура, время и объём задаются отдельными полями.
- [ ] [008] Не создавать одинаковые режимы ради разных настроек: применять профили и пресеты.
- [ ] [009] Основные настройки показывать сразу, экспертные раскрывать по запросу в стиле текущего UI.

## 3. P1 — изменения ректификации

- [x] [055] Сохранить насос backend-ом по умолчанию во всех новых и мигрированных профилях.
- [x] [056] Применять CHIM к единой запрошенной скорости до преобразования в насос или импульсы клапана.
- [x] [057] Ограничивать CHIM калибровочным диапазоном насоса и показывать факт ограничения.
- [x] [058] В автономной паузе сохранять полную флегму и не учитывать паузу как отобранный объём.
- [x] [059] Добавить опциональное дробление тела по нескольким ёмкостям через общий координатор, без второго режима ректификации.
- [x] [060] Привязать датчики уровня к активной ёмкости, а не к абстрактному «телу».
- [x] [061] Проверить совместную работу CHIM + флегмовое число + PB + смена фракции и зафиксировать приоритет условий.
  - Приоритет BODY: safety и ручная пауза → сработавший датчик уровня активной ёмкости → плановая смена ёмкости → завершение тела по PB/объёму/температуре → CHIM рассчитывает запрошенную скорость → флегмовое число или автономный цикл открывает окно отбора → backend применяет команду.
  - Поэтому CHIM не возобновляет отбор во время смены тары, а PB не позволяет начать ещё один цикл отбора после решения перейти к хвостам.
- [x] [062] Не переносить НДРФ: руководство HelloDistiller прямо указывает, что ректификация его заменяет.
  - Решение зафиксировано: отдельный режим НДРФ не добавляется. Используются существующие авторектификация, профили, CHIM, PB и фракционная программа без дублирования FSM и исполнительного тракта.

## 4. P1 — зерновой/мучной затор и пивоварение

### 4.1 Рецепт

- [x] [063] Развить MashProfile из температурных пауз в список типизированных технологических шагов.
  - Схема `type`: `heat_hold`, `heat`, `hold`, `operator_wait`, `boil`, `cool`, `stir`, `finish`; старые шаги мигрируются как `heat_hold`. До реализации исполнителей новые типы безопасно блокируют запуск, не интерпретируясь как нагрев.
- [x] [064] Поддержать: нагрев, выдержку, ожидание оператора, разваривание/кипячение, охлаждение, перемешивание и завершение.
- [x] [065] Добавить шаблоны: Солодовый профиль, Зерновой затор с развариванием, Мучной затор без разваривания, Охлаждение перед брожением.
- [x] [066] Таймер выдержки запускать только после входа в температурный допуск — текущий MASHING уже следует этому принципу.
  - Подтверждено: `inRangeStartTime` устанавливается только внутри допуска ±1°C, сбрасывается при выходе из него и является единственной точкой отсчёта выдержки и прогресса.
- [x] [067] Нулевая длительность означает явное подтверждение: засыпь, ферменты/солод, извлечение корзины, внесение хмеля.
  - В UI шаг с нулевой длительностью автоматически сохраняется как `operator_wait`: процесс ставится на паузу до явного «Продолжить».
- [x] [068] Разрешить безопасный переход к следующему шагу с записью причины в историю.

### 4.2 Разваривание и охлаждение

- [x] [069] Определять закипание по датчику пара над затором; предусмотреть резервный порог и таймаут.
- [x] [070] Для разваривания задавать максимальную мощность и длительность отдельно от обычных пауз.
- [x] [071] Реализовать периодическое охлаждение водой совместно с мешалкой для экономии воды и выравнивания температуры.
- [x] [072] Настраивать мешалку по шагам: постоянно, циклически или выключено, с пределом безопасной температуры.
  - Шаг `stir` включает постоянное перемешивание, охлаждение включает его циклически вместе с водой, остальные шаги не запускают мешалку; выше `MASH_STIRRER_SAFE_TEMP_C` мешалка блокируется.
- [x] [073] Верхний датчик уровня использовать как защиту от пены: останов нагрева, допустимое охлаждение/перемешивание и уведомление.
  - В MASHING включённый A2 трактуется как верхний датчик: отключает нагрев, включает воду и отправляет уведомление; мешалка остаётся возможной только ниже безопасной температуры.
- [x] [074] После охлаждения предлагать переход в ферментацию без обязательной автоподачи дрожжей.
  - После последнего шага охлаждения публикуется рекомендация вручную начать ферментацию.
- [x] [075] Автодозирование дрожжей разрешать только отдельным или явно переназначенным насосом; основной насос отбора нельзя занимать неявно.
  - Автодозирование не реализовано: `Pump` остаётся трактом отбора и не используется для дрожжей без отдельного назначения оборудования.

### 4.3 Без лишних режимов

- [x] [076] Несколько внесений хмеля оформить уведомлениями от времени начала кипения.
  - Шаг `boil` публикует напоминания в начале кипения, в середине и за 5 минут до завершения; время отсчитывается только после подтверждения кипения.
- [x] [077] Показывать карточку текущего шага: цель, температура, оставшееся время и действие оператора.
  - Runtime-карточка и прогресс затора получают `stepType`, целевую/текущую температуру, остаток и понятное действие оператора из live status.
- [x] [078] Не создавать разные FSM для зернового, мучного и пивного сценария: различия задаются шаблоном шагов.
  - Все шаблоны формируют один `MashProfile` и выполняются единственным `FSM::Mashing`; новый технологический сценарий добавляется последовательностью шагов, а не отдельным mode/FSM.

## 6. P1 — развитие НБК под перистальтический насос

- [x] [087] Оформить HEATING → STABILIZATION → FEED_RAMP → WORKING → FINISH вместо резкого старта полной подачи.
- [x] [088] Основной способ подачи оставить постоянным калиброванным расходом в мл/ч.
  - Явный backend текущей реализации — встроенный калиброванный перистальтический насос; фракционник голов в НБК не участвует.
- [x] [089] Добавить опциональную медленную коррекцию расхода по температуре верха колонны.
  - Коррекция выключена по умолчанию, меняет подачу не чаще раза в 30 секунд, максимум на 5% за проход и в диапазоне ±15% от калиброванного расхода.
- [x] [090] Давление применять прежде всего как ограничитель от захлёба; регулирование по давлению оставить экспертной опцией.
  - Давление ограничивает мощность и блокирует подачу через Safety V2; базовый расход остаётся калиброванным, а коррекция расхода по давлению не применяется.
- [x] [091] Ставить подачу на паузу или завершать процесс по температуре низа, давлению, скорости его роста, отказу датчика или объёму сырья.
  - Подача блокируется при невалидных температуре низа/давлении, pressure safety или anti-oscillation; по заданному объёму браги переходит в FINISH.
- [x] [092] Не возобновлять подачу после защиты без устойчивой нормализации и понятной причины.
  - После защиты подача ждёт 30 секунд устойчивых температуры и давления, публикует останов и понятную причину разрешения возобновления.
- [x] [093] Показывать заданный/фактический расход, объём браги, коррекцию и ограничивающий фактор.
  - Live status и операторская строка НБК показывают заданный, скорректированный и фактический расход, объём браги и текущий ограничитель.
- [x] [094] Не копировать аппаратные маски насоса HelloDistiller; использовать текущий драйвер и физические единицы SC-S3.
  - НБК использует только штатный `Pump::start(ml/h)` текущей платы; `feedBackend=peristaltic_internal` оставляет место для будущего внешнего backend без масок GPIO/реле сторонней прошивки.
